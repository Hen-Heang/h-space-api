# Current state of `security-api` (auth model)

This module is mid-refactor. Do not assume old README history — check current files first (`Glob security-api/src/main/java/**/*.java`) since this section can drift.

- **In**: `AuthController`, `UserController`, `AuditController`, `MfaController`, `PublicController` — JWT login/refresh/logout, MFA (`MfaService`/`MfaController`), Google login via `security/oauth/GoogleTokenVerifier` (ID-token verification, not a cookie-based OAuth2 redirect flow), audit events (`AuditEvent`, `AuditLogService`), token revocation (`RevokedToken`, `TokenBlacklistService`), `RateLimitingFilter`. Sign-in accepts an email **or a username** with the password (`UsernameRules`, `users.username`), and "continue with email" signs in or signs up with a 6-digit emailed code (`EmailLoginCodeService`, `/api/auth/email-code/*`, `email_login_codes`). That code flow was added deliberately (2026-10) and is not the removed custom OTP below — it stores only a hash, caps attempts, and still requires MFA when enabled. Password sign-up issues **no tokens** (`emailVerificationRequired: true`): the account signs in once its email is verified, and `JwtAuthenticationFilter` and `/api/auth/refresh` reject any token whose user's email isn't verified. A temporary lockout does not end existing sessions. An MFA challenge (`/api/auth/mfa/verify`) signs in once — its `jti` is revoked on success. An authenticator code is accepted once (`users.mfa_last_used_step`), and wrong codes count toward the same lockout as wrong passwords; a correct password doesn't reset that count while MFA is pending. **Sign-up is invite-only by default** (`app.signup.mode` / `SIGNUP_MODE`, `AccountAccessService`): password sign-up, a first email code and a first Google login all need a pending invite (`/api/admin/invites`, `signup_invites`) unless the email is the **owner's** (`app.owner-email` / `OWNER_EMAIL`). The owner's account is granted `ROLE_ADMIN` once its email is verified — at every sign-in and at startup — and is the only way the first admin comes to exist.
- **Temporary — Supabase bridge** (`SupabaseBridgeController`/`SupabaseBridgeService`, `security/supabase/SupabaseAdminClient`): `POST /api/auth/supabase-token` mints a short-lived HS256 token (`SUPABASE_BRIDGE_TOKEN_TTL`, default 10 minutes, capped at 15 — logout can't revoke one already issued) signed with the H-Space Supabase project's legacy JWT secret (`sub` = the user's UUID, `role`/`aud` = `authenticated`) and creates the matching `auth.users` row via the admin API on first use, so the H-Space frontend's not-yet-migrated domains keep working under Supabase RLS. Off (503) unless `SUPABASE_URL`, `SUPABASE_JWT_SECRET` and `SUPABASE_SERVICE_ROLE_KEY` are all set. Delete it once H-Space no longer queries Supabase; don't build new features on it.
- **Temporary — Supabase account import** (`SupabaseUserImportRunner`, `SupabaseUserImportService`, `security/supabase/SupabaseAuthUserReader`): one-shot command (`--supabase.import.enabled=true`, dry-run by default) copying H-Space's Supabase accounts into `users` with the same UUIDs and bcrypt hashes. Runbook: `docs/supabase-user-import.md`. Delete with the bridge.
- **Out** (removed, do not resurrect without asking): custom OTP controller/service/domain/payloads, the old cookie-based OAuth2 flow (`HttpCookieOAuth2AuthorizationRequestRepository`, `OAuth2*Handler`, `OAuth2UserInfo*`, `CookieUtils`).
- If you see references to OTP or the old OAuth2 classes anywhere (code, docs, tests), treat that as stale and flag it rather than silently reintroducing the pattern.
