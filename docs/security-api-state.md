# Current state of `security-api` (auth model)

This module is mid-refactor. Do not assume old README history — check current files first (`Glob security-api/src/main/java/**/*.java`) since this section can drift.

- **In**: `AuthController`, `UserController`, `AuditController`, `MfaController`, `PublicController` — JWT login/refresh/logout, MFA (`MfaService`/`MfaController`), Google login via `security/oauth/GoogleTokenVerifier` (ID-token verification, not a cookie-based OAuth2 redirect flow), audit events (`AuditEvent`, `AuditLogService`), token revocation (`RevokedToken`, `TokenBlacklistService`), `RateLimitingFilter`. Sign-in accepts an email **or a username** with the password (`UsernameRules`, `users.username`), and "continue with email" signs in or signs up with a 6-digit emailed code (`EmailLoginCodeService`, `/api/auth/email-code/*`, `email_login_codes`). That code flow was added deliberately (2026-10) and is not the removed custom OTP below — it stores only a hash, caps attempts, and still requires MFA when enabled. Password sign-up issues **no tokens** (`emailVerificationRequired: true`): the account signs in once its email is verified, and `JwtAuthenticationFilter` and `/api/auth/refresh` reject any token whose user's email isn't verified. A temporary lockout does not end existing sessions. `/api/auth/refresh` spends the presented refresh token with one conditional update, so it rotates once even under concurrent requests; `/api/auth/logout` is idempotent (an unknown or spent refresh token is a no-op, and the access token is still blacklisted). An MFA challenge (`/api/auth/mfa/verify`) signs in once — its `jti` is revoked on success. An authenticator code is accepted once (`users.mfa_last_used_step`), and wrong codes count toward the same lockout as wrong passwords; a correct password doesn't reset that count while MFA is pending. That lock lives in `AccountLockoutService`. **No account enumeration at login** (2026-11): the password is checked before the locked/unverified status (`WebSecurityConfig` post-authentication checks), so a wrong password always gets the generic `INVALID_CREDENTIALS`, and only the right one learns the account is locked or unverified. A wrong password on an already-locked account neither extends the lock nor resends the unlock email. **Reset token out of URLs**: validate with `POST /api/auth/reset-password/validate`; the old `GET /api/auth/reset-password?token=` is deprecated and stays only until the web app switches. **Logs**: emails and sign-in identifiers are masked (`utils/LogMasking`, e.g. `j***@gmail.com`), and reset, verification and unlock tokens are never logged; audit rows still keep the full identifier. **Sessions**: every sign-in issues its own refresh token, so signing in on a phone no longer ends the laptop's session (before 2026-11 it revoked every other token). Rotation (`/api/auth/refresh`) replaces only the presented token. **Reuse detection** (2026-11, `V7`): every sign-in starts a token family (`refresh_tokens.family_id`) that rotation carries forward, and a token spent by rotation is stamped `rotated_at`. Presenting such a token again later than `jwt.refresh-token.reuse-grace` (default 10s — two tabs racing stay harmless) revokes every live token of that family and writes a `REFRESH_TOKEN_REUSE_DETECTED` audit event; the user's other sign-ins are untouched. Tokens ended by logout, the session cap or a password reset are only refused. Each user is capped at `jwt.refresh-token.max-active-per-user` live sessions (default 10); a new sign-in over the cap drops the oldest. A password reset revokes all of the user's refresh tokens (`RefreshTokenService.revokeAllUserTokens`), because sign-in no longer does. Already-issued access tokens stay valid until they expire (24h) either way. **Step-up** (`MfaStepUpService`) re-checks the second factor for a signed-in user before a sensitive action: MFA disable, backup-code regeneration, and H-Vault reset and keyset replacement. It uses the same rules (once-only authenticator code, one-time backup code, wrong codes count toward the shared lock) and runs in its own transaction so the count survives the caller rejecting the action. Before 2026-11, MFA disable and backup-code regeneration used a plain code check: a code could be replayed and wrong guesses weren't counted. **Sign-up is invite-only by default** (`app.signup.mode` / `SIGNUP_MODE`, `AccountAccessService`): password sign-up, a first email code and a first Google login all need a pending invite (`/api/admin/invites`, `signup_invites`) unless the email is the **owner's** (`app.owner-email` / `OWNER_EMAIL`). The owner's account is granted `ROLE_ADMIN` once its email is verified — at every sign-in and at startup — and is the only way the first admin comes to exist.
- **Temporary — Supabase bridge** (`SupabaseBridgeController`/`SupabaseBridgeService`, `security/supabase/SupabaseAdminClient`): `POST /api/auth/supabase-token` mints a short-lived HS256 token (`SUPABASE_BRIDGE_TOKEN_TTL`, default 10 minutes, capped at 15 — logout can't revoke one already issued) signed with the H-Space Supabase project's legacy JWT secret (`sub` = the user's UUID, `role`/`aud` = `authenticated`) and creates the matching `auth.users` row via the admin API on first use, so the H-Space frontend's not-yet-migrated domains keep working under Supabase RLS. Off (503) unless `SUPABASE_URL`, `SUPABASE_JWT_SECRET` and `SUPABASE_SERVICE_ROLE_KEY` are all set. Delete it once H-Space no longer queries Supabase; don't build new features on it.
- **Temporary — Supabase account import** (`SupabaseUserImportRunner`, `SupabaseUserImportService`, `security/supabase/SupabaseAuthUserReader`): one-shot command (`--supabase.import.enabled=true`, dry-run by default) copying H-Space's Supabase accounts into `users` with the same UUIDs and bcrypt hashes. Runbook: `docs/supabase-user-import.md`. Delete with the bridge.
- **Out** (removed, do not resurrect without asking): custom OTP controller/service/domain/payloads, the old cookie-based OAuth2 flow (`HttpCookieOAuth2AuthorizationRequestRepository`, `OAuth2*Handler`, `OAuth2UserInfo*`, `CookieUtils`).
- If you see references to OTP or the old OAuth2 classes anywhere (code, docs, tests), treat that as stale and flag it rather than silently reintroducing the pattern.
